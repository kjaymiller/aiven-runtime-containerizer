# Examples

Each subdirectory is a self-contained `docker-compose.yaml` ("before")
plus the output of actually running `dockerize-images` against it
("after"). Run `mise run install` at the repo root first, then `cd` into
any of these and try the command in its top comment yourself --
`docker-compose.yaml` is left untouched by using `-o`, so re-running is
always safe.

| Example | Shows |
| --- | --- |
| [`basic-image-conversion/`](basic-image-conversion/) | The core `image:` -> `build:` rewrite, and exactly what compose-file formatting does and doesn't survive it. |
| [`managed-services-skipped/`](managed-services-skipped/) | Every Aiven-managed service type (pg/valkey/opensearch/kafka/clickhouse) skipped by default, plus what `--include-managed` does instead. |
| [`depends-on-ordering/`](depends-on-ordering/) | `depends_on` (both compose forms) driving build order, and why a dependency on a managed service imposes no ordering constraint. |
| [`service-binding/`](service-binding/) | `x-aiven-service:` / `--bind` / convention matching against a real Aiven project -- see the caveat below. |

## Verified vs. illustrative

`basic-image-conversion/`, `managed-services-skipped/`, and
`depends-on-ordering/` need no Aiven credentials -- their
`docker-compose.after*.yaml` files (and `docker/`/`docker-all/`
directories) are the tool's *actual* output, generated by running it
for real against the checked-in `docker-compose.yaml`.

`service-binding/` is different: binding requires a real `AIVEN_TOKEN`
and real services in a project, which isn't something to fabricate for
a shipped example. Its `docker-compose.after.illustrative.yaml` is
hand-written to show the *shape* of real output (see that file's header
comment) -- it has not been run for real. Run the command in
`service-binding/docker-compose.yaml`'s top comment yourself, against
your own project, to see the real thing.
